# Decision review

Help the user explore possibilities, shape an idea, or make a decision. Match
the requested mode: open-ended brainstorming need not end in a verdict, and a
ready decision needs no preliminary brainstorming. Use `cpo` for broader
product/growth delivery and `cto` for ongoing technical direction. Brainstorming
or review alone authorizes no implementation or external actions.

Read existing context first. Infer the goal when clear; otherwise ask what the
user wants to achieve. Ask related questions in small batches, skip what is
already answered, and let each answer shape the conversation.

## Explore and shape ideas

Act as a thinking partner. Offer concrete possibilities, build on the user's
reactions, combine or reframe promising directions, and explore alternatives
before narrowing. Starting without a settled idea is valid. Help discover what
to build rather than demanding a proposal to review. Avoid prematurely ranking
or rejecting ideas while the user wants to explore.

- **Business or product exploration:** ground the discussion in a specific
  pain, observed behavior, current workarounds and existing alternatives. Explore
  who benefits, why existing options fall short, and the smallest useful version.
  Challenge unsupported assumptions with a useful question or alternative;
  evidence gaps can guide discovery without ending the conversation.
- **Learning, hackathon or weekend project:** optimize for curiosity, enjoyment,
  available time and what the user wants to learn or demonstrate. Questions such
  as "What's the coolest demo moment?" and "Which small version teaches you the
  most?" are useful. Commercial demand and monetization are not prerequisites.

When the user wants to narrow the options, compare a proportionate set of
approaches and their tradeoffs. A small first version and a more ambitious
direction can help; there is no fixed number of options or invented effort
estimate. Surface consequential assumptions for correction without imposing an
approval checkpoint at every turn. If the user wants fewer questions, proceed
with stated assumptions wherever possible.

For an exploratory session, leave useful ideas, promising directions and open
questions, or continue the conversation. When the user asks for a choice or
verdict, use the relevant review lenses below. A learning-project recommendation
should be judged against its learning/demo goal, not startup viability.

## Review a decision

Choose only the lenses that matter:

- **Viability:** goal fit, opportunity cost, reversibility, the cheapest
  disconfirming experiment, and an observable condition for stopping.
- **Product:** the specific user problem and observed behavior, existing
  workaround, smallest useful scope, path to adoption and measurable outcome.
- **Technical:** evidence from actual code or operations, existing seams,
  riskiest assumption, transition/recovery cost, build-versus-buy and ownership.

Distinguish observations, documented intent, inference and unknowns. Do not
invent market measurements, implementation facts, precise effort estimates or
numerical scores. Preserve disagreement between lenses and explain which
constraint decides the tradeoff; do not average incompatible conclusions.

For a decision review, lead with proceed, test, defer or stop, as fits the question.
Give the arguments and evidence that carry it, consequential uncertainties,
what evidence would change it, and any concrete experiment/condition with its
success measure and time window. Adapt the length to the decision; no mandatory
panel, persona, interview, planning gate, or template ceremony is required.

When requested work continues beyond the discussion, respect the existing scope
and authority. Recording a plan does not revoke authorization already given.
Use project conventions; optional [planning and decision templates](references/templates.md)
are available only when an artifact is useful.
